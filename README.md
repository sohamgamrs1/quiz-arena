# Quiz Arena

A live multiplayer quiz game with a real-time leaderboard. A host picks a quiz from
their own bank, opens a room, shares a six-character code, and players join from a
phone or a browser. Questions are timed, scoring happens on the server, and the
leaderboard moves between questions.

Three ways to play, one engine:

- **Live room** — one host, 2 to 100 players, synchronised questions.
- **Solo run** — the same engine with one seat, for practice.
- **Async challenge** — a shareable link (`/c/<slug>`) that plays the quiz at the
  player's own pace in a private room of one.

The point of the project is the security model: the answer key never reaches a client
before the question closes, and no client can score itself. See
[ARCHITECTURE.md](ARCHITECTURE.md) for how each rule is enforced, file by file.

## Stack

| Layer | Choice |
|---|---|
| Client | Expo SDK 52 + Expo Router, TypeScript strict |
| State | Zustand for the game store, TanStack Query for reads |
| Backend | Supabase: Postgres, Auth (anonymous), Realtime, RLS |
| Styling | Plain `StyleSheet` over one design-token module, dark-first |
| Type | Inter, bundled in `assets/fonts` and loaded once in `app/_layout.tsx` |
| Icons | `@expo/vector-icons` (Ionicons) |

## Quick start

### 1. Backend

```bash
npx supabase init          # once, if supabase/config.toml is not there yet
npx supabase start         # Postgres, Auth, Realtime in Docker
npx supabase db reset      # applies supabase/migrations/*, then seed.sql
```

`db reset` prints the local API URL and anon key. The seed creates a demo host
(`demo@quizarena.local` / `quizarena`), one published quiz and the full 50-question
starter bank.

### 2. Client

```bash
cp .env.example .env
# paste the API URL and anon key printed above
npm install
npm run web        # or: npm run android / npm run ios
```

Expo will print a QR code for a physical device; make sure `EXPO_PUBLIC_SUPABASE_URL`
is reachable from the phone (use your machine's LAN IP, not `localhost`).

### 3. Play without a backend

```bash
EXPO_PUBLIC_MOCK=1 npm run web
```

Mock mode runs the whole flow — lobby, questions, reveal, leaderboard, results —
against an in-memory engine with three bots. It is development-only: the flag is
ignored when `__DEV__` is false, and its questions are about this app rather than
quiz content, so it cannot become a source of real answers.

## Design system

Dark-first, one accent, two weights, one spacing scale. The rules are enforced by the
token module rather than by discipline:

- **Type** is Inter 400 and 600 only, bundled as `.ttf` in `assets/fonts` so Android
  renders the same face as iOS and web instead of falling back to Roboto. Every size
  on screen comes from `size` in `lib/tokens.ts` via the single `T` text primitive —
  there is no ad-hoc `fontSize` anywhere in the app.
- **Identity is typographic.** No emoji avatars. A player or quiz gets a monogram tile
  whose hue is derived from the name (`lib/monogram.ts`), so the same person always
  looks the same and nothing depends on a character being rendered by the OS.
- **Colour** is near-black surfaces separated by 1px hairlines, never shadows. The
  accent appears only on the primary action and the current selection; success and
  danger are reserved for correctness.
- **Spacing** is 4/8/12/16/24/32/48 and radii are 12/16/pill. Nothing off-scale.
- **Motion** is capped at 180ms and is skipped entirely when the device asks for
  reduced motion.

## How a round works

1. `create_room(quiz_id)` mints a code and seats the host.
2. Players `join_room(code, name, emoji)`; a rejoin returns the existing seat.
3. `start_game(room_id)` stamps `question_started_at` / `question_ends_at` with the
   database clock and broadcasts `question_started`.
4. Clients read the question through `sync_room` / `get_question` — prompt, options,
   deadline, `server_now`. No key.
5. `submit_answer(room_id, question_id, option_id)` is the only write. It returns
   `{ accepted, locked_at }`. Points are computed inside the function from
   `now() - question_started_at`, never from anything the client sends.
6. Whoever notices the deadline first calls `close_question`, which writes timeout
   rows, stores the reveal, and broadcasts the key and the distribution. Everyone
   learns the answer at the same moment.
7. `next_question` advances or finishes.

Scoring, server-side only:

```
elapsed      = now() - question_started_at            (milliseconds)
speed        = greatest(0, 1 - elapsed / time_limit_ms)
points       = round(points_base * (0.5 + 0.5 * speed)) + streak_bonus
streak_bonus = 0 if wrong, else min(streak, 5) * 50
```

A wrong answer, a timeout, or an answer later than `ends_at + 750ms` scores zero and
resets the streak. Ties break on the earliest correct answer, then join order — so
two players on the same score always rank the same way twice.

## The question bank

`data/question-bank.json` is in the import shape the editor accepts (Part 4 of the
brief): 50 questions, answers spread 13/13/12/12 across a/b/c/d, difficulty 30%
easy / 50% medium / 20% hard. Paste it into the editor's import panel, or let the
seed load it.

To edit the bank, change `data/question-bank.source.json` (one entry per question,
correct answer first) and rebuild:

```bash
python3 scripts/build-bank.py   # rewrites data/question-bank.json, prints the spread
python3 scripts/build-seed.py   # rewrites supabase/seed.sql
```

CSV import accepts `prompt, option_a…option_f, correct, time_limit_ms, points_base,
explanation`. Nothing imports unless every row is valid; failures are reported with
row numbers.

## Testing the doctrine

```bash
psql "$DB_URL" -v ON_ERROR_STOP=1 -f supabase/tests/smoke.sql
```

The script runs inside a transaction it rolls back and asserts: no key in the live
payload, no correctness on submit, one answer per player enforced by the database, a
late answer stored as `rejected_late`, the key appearing only at close, deterministic
leaderboard ordering, the run finishing, and `public.questions` being unreadable to a
plain authenticated role.

The manual checks worth doing once on a real device: open DevTools → Network during a
live question and confirm no response contains the correct option; grep the web
bundle for a known answer string; kill the app mid-question and reopen it.

## Put it on GitHub

The download is a plain folder, not a git repository, so start one:

```bash
cd quiz-arena
git init
git add .
git commit -m "quiz arena: live quiz game with a server-scored leaderboard"
git branch -M main
git remote add origin https://github.com/<your-username>/quiz-arena.git
git push -u origin main
```

Nothing secret is in the tree: `.env` is ignored, `android/` and `ios/` are generated
by `expo prebuild`, and the only key anywhere in the code is a placeholder name in
`.env.example`.

Then add the two build-time values under **Settings → Secrets and variables →
Actions → New repository secret**:

| Secret | Value |
|---|---|
| `EXPO_PUBLIC_SUPABASE_URL` | your project URL |
| `EXPO_PUBLIC_SUPABASE_ANON_KEY` | the **anon** key — never the service-role key |

## Build an APK

### Free, on GitHub Actions (already configured)

`.github/workflows/android-apk.yml` runs on every push to `main`, and produces a
sideloadable APK. Nothing to set up beyond the two secrets above.

- **Push to `main`** → open the run under the *Actions* tab → download
  `quiz-arena-apk` from the run's **Artifacts** section.
- **Push a tag** → the APK is attached to the GitHub Release as well:

  ```bash
  git tag v1.0.0
  git push origin v1.0.0
  ```

- **Or** *Actions → Android APK → Run workflow* to build on demand.

The workflow installs Node 20 and JDK 17, runs `expo prebuild` to generate the native
project, and builds with Gradle. First run takes about 10–15 minutes (Gradle downloads
the Android dependencies); later runs are faster thanks to the cache.

The APK is signed with React Native's **debug keystore**. That is fine for sideloading
and testing — `adb install quiz-arena-1.0.0-42.apk` — but the Play Store will reject
it. For a properly signed release, use EAS below.

### Signed release build, with EAS

```bash
npm install -g eas-cli
eas login
eas init                                  # links the project, writes the project id
eas build -p android --profile preview    # an installable .apk
eas build -p android --profile production # an .aab for the Play Store
```

`eas.json` is already set up with a `preview` profile that builds an APK and a
`production` profile that builds an app bundle. EAS generates and holds the keystore,
so no key material ends up in the repository.

### Building locally

```bash
npm run apk     # expo prebuild + gradlew assembleRelease
```

Output lands in `android/app/build/outputs/apk/release/`. You need JDK 17 and the
Android SDK installed for this.

> **Mock mode does not work in a release build.** `EXPO_PUBLIC_MOCK` is deliberately
> gated behind `__DEV__`, so a release APK without Supabase credentials opens on the
> setup screen instead of pretending to have a backend. That is the intended
> behaviour: a shipped binary should never contain a working answer key.

## Known limits

- **Broadcast from the database.** `emit()` calls `realtime.send(...)`. If your
  Supabase project does not have that available, the call is swallowed and the app
  still works — the `room_events` change feed and the 10-second `sync_room` poll keep
  clients correct, with slightly higher latency. Nothing is lost either way.
- **The host knows the key.** They wrote the quiz. A host who wants to cheat can tell
  a friend the answer out of band; no amount of server code fixes that. What the
  design does fix is the host's client ever being a *trusted* source of scores.
- **750ms grace.** Enough for a slow mobile network on a 20-second question, small
  enough that it is not a strategy.
- **Async challenges are rooms.** Each play creates a short-lived private room. Prune
  old rooms with a cron job (`delete from rooms where status = 'finished' and
  finished_at < now() - interval '7 days'`) when you care about storage.
